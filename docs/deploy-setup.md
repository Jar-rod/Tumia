# Deploy setup: the one-off steps done by hand

Do these once, in order, before the first run of the **Deploy** workflow. After that, every deploy is
**Actions → Deploy → Run workflow**.

Everything runs in **af-south-1 (Cape Town)**. The only exception is the CloudFront certificate, which
must live in us-east-1; it holds no data.

You need: an AWS account with administrator access from your laptop (AWS CLI v2 configured), Node.js 22,
the .NET 10 SDK, a **Route 53 public hosted zone** for your domain, and admin rights on the GitHub
repository.

## 1. Enable the Cape Town region

af-south-1 is an opt-in region.

```bash
aws account enable-region --region-name af-south-1
aws account get-region-opt-status --region-name af-south-1   # repeat until it says ENABLED (can take a few minutes)
```

## 2. Write down your settings

| Setting | Example | Where it comes from |
|---|---|---|
| AWS account id | `123456789012` | `aws sts get-caller-identity --query Account --output text` |
| Domain name | `app.example.co.za` | The address users will open |
| Hosted zone name | `example.co.za` | The Route 53 zone that contains the domain |
| Hosted zone id | `Z0123456789ABCDEFGHIJ` | Route 53 → Hosted zones |
| Alert email | `ops@example.co.za` | Receives the dead-letter-queue alarm |
| CloudFront prefix list id | `pl-xxxxxxxx` | Step 3 |
| Repository OIDC subject | `Jar-rod@121164104/Tumia@<repo id>` | Step 4 |

## 3. Look up the CloudFront prefix list

The load balancer only accepts traffic from CloudFront's addresses, which AWS publishes as a managed prefix list.

```bash
aws ec2 describe-managed-prefix-lists --region af-south-1 \
  --filters Name=prefix-list-name,Values=com.amazonaws.global.cloudfront.origin-facing \
  --query 'PrefixLists[0].PrefixListId' --output text
```

## 4. Work out the repository's OIDC subject

GitHub repositories created on or after 15 July 2026 identify themselves to AWS with their numeric ids
(`owner@ownerId/name@repoId`), so a deleted-and-recreated repository with the same name cannot take over the
deploy role. This repository was created after that date.

```bash
gh api repos/Jar-rod/Tumia --jq '"\(.owner.login)@\(.owner.id)/\(.name)@\(.id)"'
```

The owner id is `121164104`. If the role cannot be assumed later ("Not authorized to perform
sts:AssumeRoleWithWebIdentity"), check the claim the workflow actually sends with
[actions-oidc-debugger](https://github.com/github/actions-oidc-debugger).

## 5. Bootstrap CDK in both regions

Run this from the **repo root** (not `infra/`), so CDK does not try to build the app yet.

```bash
npx aws-cdk@2.1147.0 bootstrap aws://<ACCOUNT_ID>/af-south-1 aws://<ACCOUNT_ID>/us-east-1
```

## 6. Create the JWT signing key

CloudFormation cannot create SecureString parameters, so this one is made by hand. It never leaves AWS.

```bash
aws ssm put-parameter --region af-south-1 --type SecureString \
  --name /prod/tumiia/jwt-signing-key \
  --value "$(openssl rand -base64 48)"
```

The origin-verify secret (the header CloudFront sends to the API) is generated by CDK in Secrets Manager.
Nobody needs to create or see it.

## 7. Deploy the GitHub deploy role from your laptop

From `infra/`, with your settings from step 2:

```bash
cd infra
npx aws-cdk@2.1147.0 deploy prod-tumiia-github-oidc \
  -c account=<ACCOUNT_ID> -c domainName=<DOMAIN> -c hostedZoneName=<ZONE_NAME> -c hostedZoneId=<ZONE_ID> \
  -c githubRepo=<OIDC_SUBJECT> -c alertEmail=<EMAIL> -c cloudFrontPrefixListId=<PREFIX_LIST_ID>
```

Copy the `DeployRoleArn` from the output.

## 8. Set up GitHub

1. **Settings → Environments → New environment** named `prod`.
   - **Deployment branches and tags:** "Selected branches and tags" → add `main`. The deploy role trusts the
     `prod` environment, so this is what limits deploys to `main`.
   - Optional: **Required reviewers**, if a second person should approve each deploy.
2. In the `prod` environment, add these **variables** (not secrets; none of them is secret):

   | Variable | Value |
   |---|---|
   | `AWS_ACCOUNT_ID` | your account id |
   | `AWS_DEPLOY_ROLE_ARN` | the `DeployRoleArn` from step 7 |
   | `DOMAIN_NAME` | e.g. `app.example.co.za` |
   | `HOSTED_ZONE_NAME` | e.g. `example.co.za` |
   | `HOSTED_ZONE_ID` | the zone id |
   | `REPO_OIDC_SUBJECT` | from step 4 |
   | `ALERT_EMAIL` | the alert address |
   | `CLOUDFRONT_PREFIX_LIST_ID` | from step 3 |

   Optional in the same environment: `ADMIN_EMAILS`, a comma-separated list of emails that get the Admin role when
   they register or sign in (needed for taxonomy settings and the feedback export). Run `infra` after changing it.

3. Optional, as a **repository** variable (Settings → Secrets and variables → Actions → Variables):
   `ARM64_RUNNER` = `ubuntu-24.04-arm`, if ARM64 runners are available to this repository. The backend image
   then builds natively instead of under emulation, which is several times faster.

## 9. First infrastructure deploy

**Actions → Deploy → Run workflow → target: `infra`.** The first run takes 20 to 30 minutes (RDS, certificates
and CloudFront are slow to create). The API service is created with **zero** tasks, because no image exists yet.

Then confirm the SNS subscription: AWS emails the alert address a link to click.

## 10. First backend deploy

**Run workflow → target: `backend`.** This builds the image, pushes it to ECR, runs the database migrations as a
one-off task, and starts the service with one task.

## 11. Email (SES)

The domain identity verifies itself once its DKIM records (created in Route 53 by the email stack) are live:

```bash
aws sesv2 get-email-identity --region af-south-1 --email-identity <DOMAIN> --query VerifiedForSendingStatus
```

**New accounts start in the SES sandbox:** email can only go to addresses you have verified
(`aws sesv2 create-email-identity --email-identity someone@example.com`). When you are ready for real users,
request production access in the SES console (Account dashboard → Request production access).

Until production access is granted, password reset emails only reach verified addresses.

## 12. Frontend

Once `apps/web` exists, **Run workflow → target: `frontend`** (or `auto`).

## Day to day

- **`auto`** deploys the frontend if `apps/web` changed, and the backend if `services/api` changed, since their
  last deploy. It never deploys infrastructure; it warns you instead.
- **`infra`** after any change under `infra/`. It reads which image the API is running first, so it never rolls
  the API back.
- The tests always run first. Nothing deploys if they fail.

## Things to know

- **Deletion protection** is on for the database. Deleting the stack will not delete it.
- **Bedrock** stays off unless you set `ENABLE_BEDROCK=true` (plus `BEDROCK_INFERENCE_PROFILE_ARN` and
  `BEDROCK_MODEL_ID`) as `prod` variables and run `infra`. Bedrock processes data **outside South Africa**.
- The **Fargate tasks run in public subnets with public IPs** (no NAT Gateway). Their security group only
  accepts traffic from the load balancer.
